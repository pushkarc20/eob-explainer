## Held-out protocol

- 15 claims with expected answers derived by hand, committed with a recorded hash before the engine or any model ran on them.
- Scenarios chosen to differ from the development set: a secondary payer, an emergency visit under a deductible, boundary cases for the thresholds, cents that do not divide evenly, a long claim, header-only amounts, and unrecognized amount categories.
- Not used for tuning. What they reveal goes to the next version's backlog.
- Limit: written by the same author and assistant as the development set, so unseen is not the same as independent.

## Decision rules (as implemented in `src/eob/decisions.py`)

Held-out set, one run per configuration, judge j2.

**A. Does prompt v2 stay the default?** Against v1 on the 15 held-out claims, all of:
1. at least 14 of 15 v2 answers pass the code checks on the first try;
2. faithfulness no more than 0.15 below v1;
3. concision at least 0.3 above v1;
4. key point no more than 0.2 below v1;
5. no leaks and no overclaiming phrases.
If two or more fail, the default returns to v1 and the README says the v2 gain did not generalize.

**B. Is a cheaper configuration recommended over medium-effort v2?** Pooled over both sets (40 claims): faithfulness within 0.2, key point within 0.3, at least 90% first-try passes, and mean cost at least 30% lower.

**C. Rules engine:** report money accuracy and flag precision and recall on the held-out set. A miss is fixed only with a written reason, and scores are shown before and after.

**D. Judge j2** changes every score, so the development set was re-scored under j2 and v0.2 claims are about j2 only.

## Outcome

Rule A: four of five criteria passed (key point failed), so v2 stays the default. Rule B: Haiku recommended, low-effort Sonnet not. Details: [v0.2_decisions.md](v0.2_decisions.md).
